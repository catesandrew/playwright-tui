## RALPLAN-DR Summary

**Principles**
1. Fast, deterministic, hermetic tests — no real browser launches, no network I/O, no real Playwright subprocess spawned by any test.
2. Test the seams that already exist as pure/isolable units (`RunController.handleReporterEvent`, `TimingHistoryStore`, `format.ts`, `PlaywrightTuiReporter`) rather than adding new production seams just to make testing easier. A structural test-double passed through an existing prop is not a new seam; a new exported interface or refactor purely for testability would be.
3. Coverage targets the highest-risk logic first: state machine correctness (`RunController`), the `TimingHistoryStore` ↔ `RunController` estimation seam, and numeric estimation correctness (`TimingHistoryStore`) — not incidental formatting.
4. Zero new production dependencies; test-only devDependencies are acceptable and minimal (this now explicitly includes `@types/bun`, required for the test files to typecheck — see iteration-1 review Finding).
5. This epic does not touch CI — out of scope per user decision (roadmap spec, "Explicitly Out of Scope").

**Decision Drivers**
1. Runtime already requires Bun (`build:exe` uses `bun build --compile`) — no reason to add a second test runner/toolchain.
2. `RunController` and `TimingHistoryStore` are the two most logic-dense, most-likely-to-regress modules in the repo (state machine + EMA math), and currently have zero coverage.
3. The reporter (`reporter/playwrightTuiReporter.cjs`) exists in **two live copies** — the standalone file and an embedded template-literal duplicate in `runController.ts` (`FALLBACK_REPORTER_SOURCE`, `runController.ts:48-236`) that is what actually runs inside the compiled `build:exe` binary when the standalone file isn't found on disk. They have already drifted (188 vs 189 lines — the on-disk file carries an `eslint-disable-next-line` comment the embedded copy lacks). Testing only the standalone copy leaves the shipped-binary code path at 0% coverage.

**Viable Options**

- **Option A — `bun test` (native), unit-first, Dashboard tested via a structural fake controller (Recommended, revised).** Use Bun's built-in Jest-compatible test runner. Write unit tests directly against exported classes/functions with synthetic inputs (no child_process, no real Playwright run, no real browser). For `Dashboard.tsx`, render it with a **structural fake controller** — a plain object implementing the exact method surface `Dashboard` calls (`getState`, `subscribe`, `isRunning`, `start`, `requestStop`, `toggleWatchMode`, `rerunAll`, `rerunFailed`), passed via `controller={fakeController as unknown as RunController}`. This requires no production code change (satisfies Principle 2 and keeps the diff additive) and never constructs a real `RunController`, so it never reaches `spawn()`.
  - Pros: zero new required runtime deps (one test-only devDependency, `@types/bun`, is required regardless — see Decision Driver / Finding below), fast, fits existing Bun-only toolchain, directly addresses the two highest-risk modules, and now correctly avoids the real-subprocess hazard the iteration-1 draft missed.
  - Cons: the fake controller's method surface can silently drift from `RunController`'s real public surface over time (mitigated below — see Risks).

- **Option B — vitest + `@vitest/ui`, unit + Ink snapshots.** Same unit test scope as A, but on vitest instead of `bun test`.
  - Pros: mature Ink-testing ecosystem examples use vitest/jest more often than bun test.
  - Cons: adds a second JS toolchain alongside Bun for no functional gain (project already requires Bun for `build:exe`); does **not** avoid the real-subprocess hazard either — `controller.start()` spawns a real process regardless of test runner, so the runner choice was never the actual risk. Rejected: the one concrete advantage (Ink-ecosystem examples) doesn't address the real blocker, so it buys nothing here.

- **Option C — Unit tests only, skip `Dashboard.tsx` testing entirely.** Cover `RunController`, `TimingHistoryStore`, `format.ts`, `PlaywrightTuiReporter` (both copies) only; explicitly exclude `Dashboard.tsx` from this epic.
  - Pros: eliminates all Ink-testing risk entirely; simplest to ship; zero exposure to Ink/Bun toolchain compatibility questions at all.
  - Cons: leaves the one user-facing rendering layer with zero coverage; iteration-1 review confirmed this option's original framing ("pre-emptively answers 'never practical' without trying") was too dismissive once a working hermetic approach (the structural fake) was found to exist, so skipping it now forfeits real, achievable value rather than avoiding a genuine blocker.

**Recommendation:** Option A, revised. The structural-fake-controller approach resolves both reviewers' central objection (Dashboard self-starting a real Playwright subprocess via `controller.start()` at `Dashboard.tsx:38-40`) without violating Principle 2, without a production code change, and without the toolchain duplication of Option B.

## Requirements Summary

Establish `bun test` as the project's test runner and add coverage for: `runController.ts` (including the retry-dedup guard and the history/ETA seam), `timingHistoryStore.ts`, `format.ts`, **both copies** of the reporter (`reporter/playwrightTuiReporter.cjs` and the embedded `FALLBACK_REPORTER_SOURCE` in `runController.ts`), and `Dashboard.tsx` via a structural fake controller. No CI wiring (explicitly out of scope). Diff is additive except for one `package.json` script line, one `@types/bun` devDependency, and a new `tsconfig.build.json` — root `tsconfig.json` itself needs no edits (verified end-to-end): keeping all test files under `src/` means they're already inside the existing `include` pattern (the typecheck boundary — so `@types/bun`, the fake-controller casts, and the `ReporterEvent` contract assertions are all actually enforced), while `tsconfig.build.json` separately excludes them from the build/publish boundary (`dist/` stays test-file-free). A single `tsconfig.json` `exclude` cannot do both jobs at once — verified empirically during review (excluding test files from typecheck silently disables it entirely, exit 0 even with real type errors present).

## Acceptance Criteria

1. `package.json` has a `"test": "bun test"` script (`package.json:16-21` — add alongside existing `dev`/`build`/`typecheck`/`build:exe` entries).
2. `bun test` exits 0 with no external network or real-browser dependency, and **no test constructs a real `RunController` instance that calls `.start()`** — `Dashboard.tsx` tests use the structural fake controller described in Acceptance Criterion 7.
3. `src/utils/format.ts` has tests covering all branches, enumerated explicitly (this corrects iteration-1's vague wording):
   - `formatDuration` (format.ts:1-16): `!Number.isFinite(ms)` (NaN/Infinity) → `'0s'`; `ms <= 0` → `'0s'`; `ms < 1_000` → `Nms`; `totalSeconds < 10` (with hours=0, minutes=0) → tenths format e.g. `'2.5s'` (line 14); `totalSeconds >= 10` with hours=0, minutes=0 → plain `Ns` (line 15); minutes > 0 branch; hours > 0 branch.
   - `truncate` (format.ts:18-23): `maxLength <= 0` → `''`; `value.length <= maxLength` → unchanged; `maxLength <= 3` → dot-repeat; else → sliced + `'...'`.
   - `percent` (format.ts:25-28): `!Number.isFinite(value)` → `0%`; value clamped below 0 → `0%`; value clamped above 1 → `100%`; mid-range rounding.
4. `src/history/timingHistoryStore.ts` has tests covering: `recordDuration` first-write path (timingHistoryStore.ts:94-101), running-average path under `MAX_TRACKED_RUNS` (timingHistoryStore.ts:104-108, `nextAvgMs` branch 2), EMA decay path at/above `MAX_TRACKED_RUNS` (same lines, branch 1, `avgMs * 0.96 + normalizedDuration * 0.04`), `clampMs` bounds (timingHistoryStore.ts:134-137), `getFallbackEstimateMs` median-of-empty vs median-of-populated (timingHistoryStore.ts:75-87), `getEstimateMs` when `enabled=false` (timingHistoryStore.ts:67-73), `load`/`save` round-trip against a temp file (created via `fs.mkdtemp`, not a fixed name) including malformed-JSON-is-non-fatal (timingHistoryStore.ts:53-65, 118-131), and `getDefaultHistoryPath` respecting `XDG_CONFIG_HOME` vs falling back to `~/.config` (timingHistoryStore.ts:27-33) — `XDG_CONFIG_HOME` is restored in `afterEach` since env is process-shared within a test file.
5. `src/controller/runController.ts`'s `handleReporterEvent` (runController.ts:571-633) has tests covering each event type (`run-begin`, `test-begin`, `test-end`, `run-end`, `fatal`) and verifying resulting `RunState` fields (via `getState()`, runController.ts:266-268), including:
   - Worker slot assignment on `test-begin` (runController.ts:804-813).
   - The **retry-dedup guard** in `finalizeTrackedTest` (runController.ts:687-692: `tracked.totalDurationMs += event.durationMs; if (!event.isFinal || tracked.finalized) return`) — synthetic `test-end` events must set `isFinal: true` to reach the counting logic at all; a dedicated test verifies a non-final retry event does **not** increment `completedTests`/`passed`.
   - Pass/fail/flaky/skipped counting branches in the `outcome` switch (runController.ts:704-742).
   - File-progress aggregation (runController.ts:834-851).
   - `clearWorker` fingerprint-mismatch bail-out (runController.ts:815-824) — a test asserts a worker slot is *not* cleared when the fingerprint doesn't match the tracked test.
   - At least one test exercises the `TimingHistoryStore` ↔ `RunController` seam with real effect, both the write direction (already covered — `recordDuration` fires from `finalizeTrackedTest:695` whenever history is enabled) and the **read** direction (not covered by a naive direct-drive test, since `historyStore.load()` is only ever called at runController.ts:343-346 inside `executeRun`, which direct `handleReporterEvent` calls never invoke — a controller built with `historyEnabled: true` alone still has an empty in-memory `tests` map). The test must construct **two** controllers driven through identical events (same fingerprint, same `phase = 'running'`, same `startedAt`) — one with a seeded timing-history JSON file at a temp path (`await (controller as any).historyStore.load()`, private readonly field, same accepted `as any` pattern as elsewhere in this epic) and one with `historyEnabled: false` (no seed) — then assert the two controllers' `updateEta` (runController.ts:859-882) results for `etaMs` **differ**. This is deliberately a differential assertion, not an exact-value one: `updateEta` reads `Date.now()` at drive time (runController.ts:870), so an exact expected `etaMs` value is inherently timing-sensitive and would flake under execution jitter (a 1ms difference in when the assertion runs shifts the computed `etaMs` by several ms once the `(1 - progress) / progress` multiplier in runController.ts:881 is applied) — a violation of Principle 1's determinism requirement, caught during review. The differential form proves the seeded history value actually reached `ensureTrackedTest`'s `getEstimateMs(...) ?? fallbackEstimateMs` (runController.ts:659) rather than always falling back, without depending on wall-clock timing.
   - Access to the private `handleReporterEvent` method is via `(controller as any).handleReporterEvent(event)` — an accepted, documented trade-off (see Risks).
6. **Both** copies of the reporter have equivalent test coverage:
   - `reporter/playwrightTuiReporter.cjs` — the test **sets `process.env.PWTUI_EVENTS_FILE` to a temp file path before constructing** `PlaywrightTuiReporter` (constructor reads the env var once, `playwrightTuiReporter.cjs:43-46`; constructing first leaves `this.eventFile = null` and `emit()` silently no-ops per `playwrightTuiReporter.cjs:179-186` and `:181-185`'s swallowed-error catch), then calls `onBegin`/`onTestBegin`/`onTestEnd`/`onError`/`onEnd` with synthetic Playwright `config`/`suite`/`test`/`result` objects (no real Playwright run), and asserts the temp file contains a **non-zero number of NDJSON lines** before asserting their shape (catches the silent-no-op failure mode directly).
   - The **embedded** `FALLBACK_REPORTER_SOURCE` copy is covered **without** regex-extracting or re-`eval`ing the raw template-literal text — both were rejected during review: the literal contains escape sequences (`\\r?\\n` at runController.ts:60, escaped `\${...}` interpolation at runController.ts:215) whose *source* text differs from their *evaluated* value, so a naive text-copy silently tests different code than what ships (e.g. a literal backslash-r instead of a real regex escape) while still compiling and passing — a worse failure mode than no coverage at all, because it's silent. Instead: construct a `RunController`, temporarily stub `fs.existsSync` — scoped by path (delegate to the real function for everything except the `playwrightTuiReporter.cjs` path, restore in `afterEach`) and with `process.env.PWTUI_REPORTER_PATH` cleared first (that env var is checked *before* the on-disk tier, runController.ts:917-920, and would make the stub irrelevant if a developer has it set locally) — so `resolveReporterRuntime()`'s tier-2 check fails, call `(controller as any).resolveReporterRuntime()` directly, and use the returned `path` — `resolveReporterRuntime()` (runController.ts:929-933) already correctly evaluates the template literal and writes real, valid `.cjs` source to a temp file as part of its normal tier-3 fallback behavior, so this reuses production logic instead of re-deriving it. `require()` (via `createRequire(import.meta.url)`, not a static `import`, which fails typecheck against a `.cjs` with no declaration file) that returned path and run it through the **same** behavioral assertions as the standalone file (call the returned `cleanup()` afterward). This covers the exact code path that runs inside the compiled `build:exe` binary.
   - Both reporter tests **must** live under `src/` (e.g. `src/reporter/playwrightTuiReporter.test.ts`, `src/reporter/playwrightTuiReporterEmbedded.test.ts`) — not in the top-level `reporter/` directory. This is mandatory, not implementer's choice: `tsconfig.json`'s `rootDir: "src"` means adding a `reporter/**/*.test.ts` include pattern instead produces `TS6059: File '.../reporter/x.test.ts' is not under 'rootDir'`, failing `bun run typecheck` unconditionally (verified during review). Both are written as `.test.ts`, importing `ReporterEvent` from `src/types.ts` and asserting each parsed NDJSON line satisfies the type shape via a **real runtime type guard**, not a bare type annotation — `JSON.parse(line)` returns `any`, and `any` is silently assignable to `ReporterEvent`, so `const ev: ReporterEvent = JSON.parse(line)` typechecks and passes even for garbage content (verified during review: a JSON string with a nonsense `type` field and wrong field types still typechecks with zero errors under this pattern). Instead: parse into `unknown`, then narrow through a hand-written guard with real field checks — e.g. `function assertIsReporterEvent(v: unknown): asserts v is ReporterEvent`, switching on `v.type` with a `never`-typed default branch so a future `ReporterEvent` variant that this guard doesn't handle fails to compile — or construct each expected NDJSON line as a literal that `satisfies ReporterEvent` and compare against the parsed value (verified both forms actually produce compiler/runtime errors on a bad shape, unlike the bare annotation). This is the only real contract enforcement that exists for the reporter — it is plain, unchecked JavaScript **outside** `tsconfig.json`'s `include` by default, and `handleReporterEvent`'s switch (runController.ts:572-632) has no `default` case, so an undetected shape drift degrades the app silently at runtime rather than failing loudly.
7. `Dashboard.tsx` has snapshot/interaction tests rendered against a **structural fake controller**, typed precisely as `Pick<RunController, 'getState' | 'subscribe' | 'isRunning' | 'start' | 'requestStop' | 'toggleWatchMode' | 'rerunAll' | 'rerunFailed'>` (exactly the 8 methods `Dashboard.tsx` calls — verified against every call site: `getState` line 23, `subscribe` line 36, `start` line 39, `isRunning` lines 52/123/145/155, `requestStop` line 124, `toggleWatchMode` line 139, `rerunAll` line 150, `rerunFailed` line 164) and passed as `controller={fakeController as unknown as RunController}`. Using `Pick<...>` rather than an untyped plain object gives compile-time signature checking on every member the fake provides — a real safety net once these test files are inside the typecheck boundary (Implementation Step 2). The fake's `subscribe` **must** return a cleanup function (`Dashboard.tsx:36` — `useEffect(() => controller.subscribe(setState), [controller])` uses the return value as the effect's cleanup; returning `undefined` throws React's "effect function must not return anything besides a function used for clean-up") and **must** call the listener synchronously once, matching the real `RunController.subscribe`'s behavior (runController.ts:272), so initial-render behavior doesn't diverge from production. The fake's `start()` is a no-op that never calls a real `RunController.start()`, so no subprocess is ever spawned. Uses Ink's own test rendering (`ink-testing-library` if it proves Bun/Ink-5 compatible, otherwise Ink's `render` against a fake writable stream — implementer's choice, documented in the PR; `Dashboard.tsx:208-209`'s `stdout?.columns ?? 120` / `stdout?.rows ?? 40` fallbacks mean a fake stream lacking `.columns`/`.rows` degrades gracefully rather than producing `NaN` layout). At minimum: a snapshot with a synthetic `RunState` mid-run, and one interaction test (e.g. pressing `s` toggles the summary panel via `Dashboard.tsx:133-134`'s `useInput` handler).
8. Diff is additive: new test files (all under `src/`), two `package.json` script-line changes (add `"test"`; modify `"build"` to point at `tsconfig.build.json` — see Implementation Step 2), one `@types/bun` devDependency (`package.json` devDependencies + lockfile), and a new `tsconfig.build.json` — root `tsconfig.json` itself needs **zero edits** (verified end-to-end: reporter tests under `src/` are already covered by the existing `include: ["src/**/*.ts", "src/**/*.tsx"]`, and `@types/bun` is auto-discovered alongside `@types/node` with no `"types"` array needed) — no other production `.ts`/`.tsx`/`.cjs` file's runtime behavior changes.

## Implementation Steps

1. Add `"test": "bun test"` to `package.json` scripts (package.json:16-21).
2. Add `@types/bun` as a devDependency (`bun add -d @types/bun`) — required because `tsconfig.json:18`'s `include: ["src/**/*.ts", "src/**/*.tsx"]` pulls every `src/**/*.test.ts` into `bun run typecheck`, and without Bun's ambient types, `import { test, expect } from 'bun:test'` fails with `TS2307`. Verified during review: `@types/bun@1.4.1` and the existing `@types/node@22.20.1` coexist cleanly with no `"types"` array needed — `bun:test` resolves and real type errors still fail (exit 2). **Do not** add test files to `tsconfig.json`'s `exclude` — that was tried and rejected during review: `exclude` governs both emit and `--noEmit` typecheck, so excluding test files to keep them out of `dist/` also silently removes them from typecheck entirely (verified empirically: `tsc --noEmit` exits 0 even with a deliberate type error in an excluded test file). **Do not** add a `reporter/**/*.test.ts` include pattern either — `tsconfig.json:8`'s `rootDir: "src"` rejects any included file outside `src/` with `TS6059` (verified empirically), so this would break `bun run typecheck` unconditionally; instead the reporter tests are placed under `src/` (Acceptance Criterion 6, Implementation Steps 5-6), which already satisfies `include: ["src/**/*.ts", ...]` with no config change needed. The only tsconfig change is: create a separate **`tsconfig.build.json`** that extends `tsconfig.json` and adds `"exclude": ["**/*.test.ts", "**/*.test.tsx"]`; change `package.json`'s `"build"` script to `"tsc -p tsconfig.build.json"` (`"typecheck"` stays pointed at the root `tsconfig.json`, so it keeps checking test files, wherever under `src/` they live). `build:exe` is unaffected either way — `bun build --compile` bundles from `src/cli.tsx` and never reaches test files regardless of tsconfig.
3. `src/utils/format.test.ts` — pure-function tests per the branch enumeration in Acceptance Criterion 3, no setup required.
4. `src/history/timingHistoryStore.test.ts` — use `fs.mkdtemp(path.join(os.tmpdir(), 'pwtui-history-'))` for isolated temp file paths per test (mirrors the module's own `mkdir`/`writeFile`/`rename` pattern at timingHistoryStore.ts:118-131); clean up temp dirs in `afterEach`; restore `XDG_CONFIG_HOME` in `afterEach`.
5. `src/reporter/playwrightTuiReporter.test.ts` (under `src/`, not the top-level `reporter/` dir — see Acceptance Criterion 6) — load the `.cjs` module via `createRequire(import.meta.url)` (a static `import Reporter from '../../reporter/playwrightTuiReporter.cjs'` fails typecheck with `TS7016: Could not find a declaration file`, verified during review; `createRequire` typechecks clean and works correctly under Bun); construct-order matters (env var set before `new PlaywrightTuiReporter()` — see Acceptance Criterion 6); synthetic Playwright objects; temp `PWTUI_EVENTS_FILE`; assert non-zero NDJSON line count, then run each parsed line through the runtime type guard described in Acceptance Criterion 6 (not a bare type annotation).
6. `src/reporter/playwrightTuiReporterEmbedded.test.ts` — construct a `RunController`, stub `fs.existsSync` so the on-disk `reporter/playwrightTuiReporter.cjs` path resolves as missing, call `(controller as any).resolveReporterRuntime()` directly to obtain the temp path + `cleanup()` that `resolveReporterRuntime()`'s tier-3 fallback (runController.ts:929-933) writes from the already-evaluated `FALLBACK_REPORTER_SOURCE`, `require()` (via `createRequire`, same as Step 5) that path, and run it through the identical assertions as Step 5. The stub is **not** a blanket `() => false`: delegate to the real `existsSync` for every path except the one ending in `playwrightTuiReporter.cjs` (a process-global blanket stub can disturb unrelated `existsSync` callers during the test), and restore the original in `afterEach`. Also clear/delete `process.env.PWTUI_REPORTER_PATH` before calling `resolveReporterRuntime()` — it's checked *first*, before the on-disk tier (runController.ts:917-920), so a developer's local env leaking that variable would make the stub irrelevant and silently test the wrong file. Do **not** regex-extract or re-`eval` the raw template-literal text (see Acceptance Criterion 6 for why: the escape sequences at runController.ts:60 and :215 make a naive text-copy silently test different code than what ships). Call `cleanup()` in `afterEach`.
7. `src/controller/runController.test.ts` — construct `RunController` with a minimal `RunControllerOptions` (`historyEnabled: false` for most tests to avoid filesystem I/O; note `exactOptionalPropertyTypes: true` in `tsconfig.json:16` means `historyFilePath` must be passed explicitly, e.g. `historyFilePath: undefined`), drive it via `(controller as any).handleReporterEvent(event)`, assert via `getState()`. One dedicated test (Acceptance Criterion 5's last bullet) constructs **two** controllers driven through identical events — one seeded via a temp history file + `await (controller as any).historyStore.load()`, one with `historyEnabled: false` — both with `phase = 'running'` and the same `startedAt`, and asserts their `etaMs` results differ (a differential comparison, not an exact expected value, since `updateEta` reads the wall clock at drive time).
8. `src/tui/Dashboard.test.tsx` — define the `Pick<RunController, ...>`-typed structural fake controller object (see Acceptance Criterion 7, including the `subscribe` cleanup-function and synchronous-listener-call requirements) and render `Dashboard` with it via `controller={fakeController as unknown as RunController}`. Attempt `ink-testing-library` first; if it proves incompatible with Bun's test runner or Ink 5, fall back to Ink's own `render()` with a fake writable stream and document the choice in the PR — either way the fake controller (not tooling compatibility) is what makes this hermetic, so this criterion cannot silently pass without real coverage.
9. Run `bun test`, `bun run typecheck` (root `tsconfig.json`, test files present and actually checked), and `bun run build` (now `tsc -p tsconfig.build.json`; confirm no `.test.*` files land in `dist/`) locally; all three must pass before this epic's bead is closed.

## Risks and Mitigations

|---|---|
| Structural fake controller's method surface drifts from `RunController`'s real public surface over time (e.g. a new method `Dashboard` starts calling isn't added to the fake) | The `Pick<RunController, ...>` typing (Acceptance Criterion 7) gives compile-time signature checking on every member the fake provides. Runtime drift on a path the tests don't exercise (e.g. a future keybinding calling a method no existing test presses) would not be caught by that alone — the accepted residual risk is scoped to "any test that exercises the affected path gets an immediate `TypeError`," not "any drift anywhere is caught," which is a narrower and more honest claim than iteration-2's |
| Accessing `RunController`'s private `handleReporterEvent` for testing feels like a layering violation | Accepted trade-off — the alternative (spawning a real child process per test) makes tests slow/flaky and defeats Principle 1; documented in Implementation Step 7 |
| `TimingHistoryStore` tests writing to a shared/real `~/.config/playwright-tui/history.json` during test runs | Every test uses an isolated `mkdtemp` path, never the real default path — explicit acceptance criterion (#4) |
| Reporter test asserts against internal event shape that later drifts from `src/types.ts`'s `ReporterEvent` type | **Corrected from iteration 1:** the reporter is plain `.cjs`, outside `tsconfig.json`'s `include`, so there is **no** existing compile-time contract tying it to `ReporterEvent` — this is exactly why the test matters (it's the only enforcement that will exist), not a redundant safety net. | The reporter exists in two copies (`reporter/playwrightTuiReporter.cjs` and embedded `FALLBACK_REPORTER_SOURCE` in `runController.ts:48-236`) that can drift silently, and only the standalone copy is what most obviously gets tested | Acceptance Criterion 6 explicitly requires equivalent coverage of both copies, since the embedded copy is what runs inside the compiled `build:exe` binary |

## ADR: Test Infrastructure Approach for playwright-tui

**Decision:** Adopt `bun test` (Bun's native, Jest-compatible test runner) for all Epic 1 coverage, test `Dashboard.tsx` via a `Pick<RunController, ...>`-typed structural fake controller passed through the existing `controller` prop rather than any production refactor, cover both live copies of the Playwright reporter (standalone `.cjs` and the embedded `FALLBACK_REPORTER_SOURCE` in `runController.ts`) via `resolveReporterRuntime()`'s own tier-3 fallback logic, and split `tsconfig.json`/`tsconfig.build.json` so test files sit inside the typecheck boundary and outside the build/publish boundary.

**Drivers:** (1) Bun is already a hard runtime requirement (`build:exe`), so a second test toolchain (vitest) would add maintenance surface for no functional gain. (2) `RunController` and `TimingHistoryStore` are the highest-risk, highest-regression-likelihood modules with zero existing coverage. (3) The reporter's dual-copy duplication (already drifted by one comment) meant naive coverage of only the standalone file would leave the code path that runs inside the compiled `build:exe` binary completely untested. (4) Production code must stay untouched — Principle 2 forbids adding new seams purely for testability.

**Alternatives considered:**
- *vitest/jest as the test runner* — rejected: the one real advantage (richer Ink-testing ecosystem examples) doesn't address the actual blocker (Dashboard spawning a real subprocess on mount), which is runner-independent, so it would have added toolchain duplication for zero benefit.
- *Skip `Dashboard.tsx` testing entirely* — considered seriously after the structural-fake-controller approach was found to work; rejected because a genuine hermetic path exists, so skipping would forfeit real, achievable coverage of the one user-facing rendering layer.
- *Export `Dashboard.tsx`'s presentational sub-components as a production container/presentational split* (Architect's iteration-1 synthesis) — a legitimate alternative with real long-term separation-of-concerns value, but rejected in favor of the structural fake controller because it achieves equivalent hermetic coverage without any production code change, keeping the diff fully additive.
- *Regex-extract or re-`eval` the embedded reporter copy's raw template-literal text* — rejected: escape sequences in the source differ from their evaluated form, so naive text-extraction would silently test different code than what ships (a worse failure mode than no coverage, because it's silent) while still compiling and passing.
- *A single tsconfig.json `exclude` for both the typecheck and emit boundaries* — rejected: verified empirically that `exclude` governs both, so excluding test files to keep `dist/` clean also silently disables typechecking them.

**Why chosen:** Each element of the chosen approach was validated against the actual codebase (not assumed) across four consensus iterations by two independent reviewers, converging on zero open objections. The structural fake controller closes the one real hermeticity hazard (a self-starting Playwright subprocess) without any production change. The tier-3-fallback-reuse approach for the embedded reporter copy exercises real production logic instead of re-deriving fragile extraction. The tsconfig split resolves the typecheck/emit boundary conflict that a single config cannot.

**Consequences:** Three new test-only files-of-concern going forward: the structural fake controller's method surface must be kept in sync with any new `RunController` methods `Dashboard.tsx` starts calling (compile-time-checked via `Pick<...>`, but only for paths tests actually exercise); the dual-reporter-copy duplication itself remains unfixed (tested around, not resolved — tracked as a follow-up); and `tsconfig.build.json` must be kept in sync with any future test-file naming convention changes (currently `**/*.test.ts`/`**/*.test.tsx`).

**Follow-ups:** File a bead for reporter de-duplication (single source of truth for `playwrightTuiReporter.cjs`, e.g. generating the embedded constant from the standalone file at build time). No other follow-ups — CI/lint wiring remains explicitly out of scope for this epic per the parent roadmap spec.
