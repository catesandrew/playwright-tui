# Epic 2: Config File Support

Status: pending approval (consensus reached — Architect: architecturally sound; Critic: approve with improvements, applied, no further review round needed)
Bead: playwright-tui-777
Spec: .internal/specs/2026-09-06-playwright-tui-roadmap-design.md#epic-2--config-file-support
Mode: consensus (RALPLAN-DR short), non-interactive

## RALPLAN-DR Summary

**Principles**
1. CLI flags always win over config file values, which always win over built-in defaults — three-tier precedence, no silent merging ambiguity.
2. Fail fast and loud on any invalid **config file that is actually being used as a config source** — malformed JSON, a non-object root, an unknown key, or a wrong-typed known key all throw a descriptive, file-path-naming error. This does **not** extend to `package.json` when it's merely being probed as a fallback location and doesn't contain a `"playwright-tui"` key at all — see Acceptance Criterion 1's explicit scoping, corrected during review after both reviewers found the original wording ambiguous about this exact case.
3. When both `.playwright-tuirc.json` and a `package.json` `"playwright-tui"` key exist in the target directory, the standalone file wins entirely — the `package.json` key is ignored, not merged (per the roadmap spec's stress-test resolution).
4. Config values that have a CLI-flag equivalent are normalized identically to that flag's own normalization, but resolved against the config-file's own directory rather than the process's — a config-sourced `historyFile` is computed as `path.resolve(cwd, expandHomePath(value))`, **not** the flag's literal `path.resolve(expandHomePath(value))` (which resolves against `process.cwd()`) — corrected during review after both reviewers found the original draft let config-sourced paths silently diverge from flag-sourced ones, and a follow-up review round found the "same as the flag" phrasing was itself ambiguous about the resolution base.
5. Zero new runtime dependencies — config parsing uses `JSON.parse` and hand-written validation, no schema-validation library, since the config surface (3 fields) doesn't justify one.
6. Tests for this epic's config-loading logic are added once Epic 1's `bun test` harness exists (Epic 1 is a soft prerequisite per the roadmap spec's sequencing — Epic 2 can be implemented before Epic 1 finishes, but its own tests land in the same harness).

**Decision Drivers**
1. `src/cli.tsx`'s current `parseArgs` (cli.tsx:50-170) has no concept of "was this value explicitly set by a flag, or is it still the built-in default" — `historyEnabled`, `historyFilePath`, and `runner` are initialized to hard defaults at cli.tsx:52-54 and only mutated when a matching flag is encountered. Config-file values need to slot in *between* "unset" and "built-in default", so this tracking must be added.
2. Config lookup depends on the resolved `cwd` (`-C`/`--cwd`, cli.tsx:85-100), which is itself parsed from argv — so config loading must happen *after* argv parsing determines the target directory, not before. It must **also** be skipped entirely for the `kind: 'help'` and `kind: 'version'` results (cli.tsx:77-83), which `main()` returns before ever constructing `RunController` (cli.tsx:25-33) — corrected during review: a user checking `--help` because they have a typo'd config file must not be blocked by that same typo.
3. Existing error handling (cli.tsx:246-250: catch, print `Error: <message>`, exit 1) already provides a fail-fast surface for thrown errors — config validation errors can reuse this path with no new error-handling machinery.
4. `path.resolve(expandHomePath(value))` (cli.tsx:119, :126) is the CLI flag's normalization for `historyFilePath`; nothing downstream (`TimingHistoryStore`'s constructor, timingHistoryStore.ts:42, or its `save()`, timingHistoryStore.ts:118-131) does any further normalization — all path hygiene lives in `parseArgs` today, so config-sourced values must go through the identical normalization before reaching the same consumer, or they'll silently misbehave (e.g. a literal `~` directory created under the process CWD) — found during review.

**Viable Options**

- **Option A-prime — Keep `parseArgs`'s return fully-populated `CliOptions`, add an additive `explicitKeys` set (Recommended, revised from iteration 1's Option A).** `parseArgs` continues to return a complete, valid `CliOptions` at every stage (unchanged from today), but its `kind: 'run'` result gains one additive field: `explicitKeys: ReadonlySet<'historyEnabled' | 'historyFilePath' | 'runner'>`, populated by each flag-matching branch alongside its existing assignment (six branches: `--history` cli.tsx:102, `--no-history` cli.tsx:108, `--history-file` cli.tsx:114, `--history-file=` cli.tsx:124, `--runner` cli.tsx:131, `--runner=` cli.tsx:141). A new `src/config/loadConfig.ts` module resolves and validates the config file for a given `cwd`. `main()` composes: parse argv → for `kind: 'run'` only, resolve `cwd` → load config → for each of the three tracked keys, if absent from `explicitKeys` and the config supplies a (normalized) value, override it in the already-complete `options` object → construct `RunController`.
  - Pros: `CliOptions`/`ParseResult`'s existing shape is unchanged, so `main()`'s existing consumption (cli.tsx:35-36) and any future Epic-1 tests written against `parseArgs`'s current contract keep working — the change is purely additive, which directly shrinks this epic's top-ranked risk (a regression in the working argv-parsing loop) from "the whole return shape changed" to "one more field got added". `loadConfig` stays independently unit-testable as a pure `(cwd: string) => PlaywrightTuiConfig` function regardless of this choice.
  - Cons: the three flag-matching branches each carry two obligations now (assign the value, and add the key to `explicitKeys`) — missing the second in exactly one branch produces a precedence bug invisible to `tsc` and only caught by a test exercising that flag's exact spelling; this residual risk is addressed by widening Acceptance Criterion 7's required test coverage to include both spellings of every affected flag (see below), rather than by a structural guarantee.

- **Option B — Pre-scan `cwd` once (`resolveCwd(argv)`), load config, then call the existing `parseArgs(argv, config)` with config seeding the three locals' initial values instead of hard defaults.** Considered properly this round (iteration 1 dismissed it on a claim — that it "doesn't avoid the -C ordering constraint, it just hides it" — that doesn't hold up: `-C`/`--cwd` can only appear in the leading wrapper-option run before `parseArgs` hits its `--` separator (cli.tsx:64) or its first-unrecognized-token early return (cli.tsx:148), so a bounded `resolveCwd` pre-scan is genuinely short and well-defined, not equivalent-in-disguise to Option A-prime).
  - Pros: `parseArgs`'s return shape stays completely untouched (not even an additive field), `config` arrives as an ordinary parameter so `parseArgs` remains trivially unit-testable in isolation, and precedence falls out "for free" from the existing seed-then-overwrite pattern the loop already uses for hard defaults — no `explicitKeys` bookkeeping to forget.
  - Cons: real cost is duplicated `-C`/`--`/early-return logic between the new `resolveCwd` pre-scan and the existing loop's own handling of those same tokens — two places that must be kept in sync as argv-parsing evolves, a maintenance hazard Option A-prime doesn't have since there's only one pass over argv. Also loses the "assigning the local IS the explicit-override signal" property for any *future* field whose precedence logic needs to be more than last-write-wins (e.g. a hypothetical field where "explicitly set to the same value as default" must still be distinguishable from "left at default") — not a concern for this epic's three fields, but the roadmap's Epic 3 adds a fourth config field (default project filter) that may need exactly this distinction.

- **Option C — Load config eagerly from `process.cwd()`, before any argv parsing, ignore `-C`/`--cwd` for config lookup.** Simplest possible sequencing: config is always read from the invocation directory, never the `-C`-resolved target directory.
  - Pros: no ordering dependency between argv parsing and config loading at all.
  - Cons: actively wrong for the documented `-C`/`--cwd` use case (README: "Run against a different project directory") — a config file in the *target* Playwright project (where a team would naturally keep project-specific defaults) would never be found; rejected as it silently breaks the most likely real-world use of both features together.

**Recommendation:** Option A-prime. It keeps precedence logic in one visible merge step (Option A's original win) while eliminating iteration-1's real weakness (a changed return-type payload rippling through every consumer) by making the change purely additive — directly addressing this epic's top-ranked risk. Option B is a legitimate, closely-argued alternative rejected specifically on maintenance-duplication grounds (two independent bits of `-C`/`--` handling), not on the mischaracterized ordering claim iteration 1 used.

## Requirements Summary

Add support for `.playwright-tuirc.json` (or, if absent, a `"playwright-tui"` key in `package.json`) in the resolved `--cwd` target directory, providing defaults for `history`, `historyFile`, and `runner` that CLI flags override and built-in defaults fall back from. Config-sourced `historyFile` values are normalized identically to the `--history-file` flag. Malformed or type-invalid config (when actually present as a config source) fails fast with a field- or file-naming error; a `package.json` with no `"playwright-tui"` key is never treated as an error source, whether or not it parses. Config loading is skipped entirely for `--help`/`--version`. Update `docs/docs/usage.md` to document the feature as part of this epic (not deferred to Epic 4, per the roadmap spec's stress-test resolution).

## Acceptance Criteria

1. A new `src/config/loadConfig.ts` exports `loadConfig(cwd: string): PlaywrightTuiConfig`, where `PlaywrightTuiConfig` is defined in `src/types.ts` (per the roadmap spec's explicit instruction — see Implementation Step 1 for the resolved AC6/spec-alignment discussion). It:
   - Checks for `path.join(cwd, '.playwright-tuirc.json')` first. If it exists: reads and `JSON.parse`s it (read and parse failures both produce a single descriptive error naming the file path — see the error taxonomy below); validates the parsed root is a non-null, non-array object (if not, throws an error naming the file path and the actual type found, e.g. `"array"`, `"null"`, `"number"`); validates exactly three optional fields (`history: boolean`, `historyFile: non-empty string`, `runner: 'auto' | 'bunx' | 'npx'`); silently ignores an optional `"$schema"` key if present (cheap, forward-compatible allowance for editor tooling — does not count as an unknown key); rejects any other key present with an error naming the key and the file path. **Does not** look at `package.json` at all in this case, even if it also has a `"playwright-tui"` key (no merge — the standalone file wins entirely).
   - If `.playwright-tuirc.json` doesn't exist: attempts to read and parse `path.join(cwd, 'package.json')`. **Scoped fail-fast behavior** (Principle 2): if `package.json` is missing, unreadable, fails to `JSON.parse`, or **parses successfully to a non-object root** (`null`, an array, or a primitive — e.g. a `package.json` containing literally `null`, which would otherwise throw a raw `TypeError` on property access), `loadConfig` returns an empty config (`{}`) with **no error** — `package.json` is being probed as a fallback location, not asserted to exist or be valid, and most target directories won't have opted into this feature at all. If `package.json` *does* parse to an object but has no `"playwright-tui"` key (or the key is `undefined`), also returns `{}` with no error. **Only once a `"playwright-tui"` key is actually present** does the same validation as the standalone-file case apply (non-object-root check on the *key's value*, three-field validation, unknown-key rejection) — from that point on, an invalid value **does** throw, since the user has now opted in.
2. `src/cli.tsx`'s `parseArgs` (cli.tsx:50-170) gains one additive field on its `kind: 'run'` result: `explicitKeys: ReadonlySet<'historyEnabled' | 'historyFilePath' | 'runner'>`. Each of the six flag-matching branches that currently assigns one of these three locals (`--history` cli.tsx:102-106, `--no-history` cli.tsx:108-112, `--history-file` cli.tsx:114-122, `--history-file=` cli.tsx:124-129, `--runner` cli.tsx:131-139, `--runner=` cli.tsx:141-146) also adds the corresponding key to the set being built. `cwd` is **not** part of this tracking — it always resolves to either the `-C`/`--cwd` value or `process.cwd()`, since config lookup needs a concrete directory regardless of whether it was explicitly passed, and a `"cwd"` key in a config file is rejected outright by Acceptance Criterion 1's unknown-key check (this is a deliberate non-goal: config cannot relocate the directory it was itself loaded from — a config-supplied `cwd` would be a bootstrapping paradox). `CliOptions`'s existing shape and every other part of `ParseResult` (`kind: 'help'`, `kind: 'version'`, the `playwrightArgs` slicing) are unchanged.
3. A new merge step (in `src/cli.tsx`, near `main()`) applies, only when `parsed.kind === 'run'`: for each of `historyEnabled`, `historyFilePath`, `runner` — if the key is **not** in `explicitKeys` and `loadConfig(cwd)`'s result has a value for it, override `options`'s existing value with the config's value (normalized, for `historyFile`, per below); otherwise leave `options`'s existing (flag-set or hard-default) value untouched. A config-sourced `historyFile` is normalized as **`path.resolve(cwd, expandHomePath(value))`** — note this is *not* the same expression as the CLI flag's own `path.resolve(expandHomePath(value))` (cli.tsx:119, :126), which resolves against `process.cwd()`; the config version pins the base to the resolved `cwd` (the directory the config file itself lives in) instead, since that's the one interpretation that keeps a committed, project-local config portable regardless of the invocation directory. This normalization happens in this merge step, inside `src/cli.tsx` — see Implementation Step 2 for why it cannot live inside `loadConfig.ts`.
4. `main()` (cli.tsx:23-48) calls `loadConfig(cwd)` and applies Acceptance Criterion 3's merge **only on the `kind: 'run'` branch**, after `cwd` is known and before constructing `RunController` — never for `kind: 'help'` or `kind: 'version'`, which must keep working even when the target directory's config file is invalid. Any error thrown by `loadConfig` (per Acceptance Criterion 1's error taxonomy) propagates through the existing top-level `.catch` (cli.tsx:246-250), which already prints `Error: <message>` to stderr and exits 1 — no new error-handling path is needed.
5. `main()`'s headless path (`runHeadless`, cli.tsx:172-202) is extended to print the resolved command once, the first time `state.command` becomes non-empty — mirroring the existing `printedHeader` latch pattern (cli.tsx:173-181) with a new `printedCommand` latch, e.g. `if (state.command && !printedCommand) { process.stdout.write(\`Command: ${state.command}\n\`); printedCommand = true }`. This is a small, independently-useful fix (headless mode currently never surfaces the resolved runner/command at all — a pre-existing gap, not something this epic introduces) that also makes Verification Step 3 below actually observable; found necessary during review after the original verification approach was shown to observe output the TUI never produces.
6. `docs/docs/usage.md` gains a new section documenting: the two supported config file locations and their precedence (standalone file wins, no merge, and there is **no** upward directory traversal — lookup is `cwd`-only, unlike `.eslintrc`-style ancestor walks); the three supported fields and their CLI-flag equivalents, explicitly noting `historyFile` gets the same tilde-expansion/path-resolution treatment as `--history-file`; that CLI flags always override the config file; that malformed/invalid config (once actually present as a config source) produces a fail-fast error rather than being silently ignored; and that an absent or unrelated `package.json` (no `"playwright-tui"` key) is never treated as an error.
7. Diff is scoped to: `src/cli.tsx`, the new `src/config/loadConfig.ts`, `src/types.ts` (the new `PlaywrightTuiConfig` type, per Acceptance Criterion 1), `docs/docs/usage.md`, and — once Epic 1's harness exists — `src/config/loadConfig.test.ts`. No change to `RunController`'s public options contract (`RunControllerOptions`, runController.ts:24-30).
8. Tests for `loadConfig`, the merge/precedence logic, and headless command printing are written once Epic 1's `bun test` harness exists (`src/config/loadConfig.test.ts`), covering at minimum: config-file-only (no CLI flags) uses config values; each of the three fields' CLI flag overrides an opposing config value, including **both spellings** where two exist (`--history-file` and `--history-file=`; `--runner` and `--runner=`); the specific case of an explicit `--history` flag (which sets `historyEnabled = true`, identical to the built-in default) correctly winning over a config `history: false` — the one precedence case where "explicit flag" and "still at default" produce the same value and are easy to conflate; both config sources present → standalone file wins, `package.json` key ignored entirely; malformed JSON in the standalone file fails with a path-naming error; a non-object root (`null`, `[]`, a bare number/string) in the standalone file fails with a type-naming error; a wrong-typed known field fails with a field-naming error; an unknown key fails with a key-naming error; a target directory with **no** `.playwright-tuirc.json` and **no** `package.json` at all falls through cleanly to built-in defaults with no error; a target directory with a `package.json` that has no `"playwright-tui"` key falls through cleanly with no error, even if that `package.json` is otherwise malformed JSON; `historyFile` tilde-expansion (`{"historyFile": "~/scratch/history.json"}`) resolves the same way the CLI flag would. This criterion documents the test scope now so Epic 1's harness has a ready-made target; it does not block Epic 2's own implementation from landing first.

## Implementation Steps

1. Add `interface PlaywrightTuiConfig { history?: boolean; historyFile?: string; runner?: RunnerMode }` to `src/types.ts`, reusing the existing `RunnerMode` type export from `runController.ts:21`. This resolves iteration-1's contradiction between the roadmap spec ("document the shape in `src/types.ts`") and the plan's own acceptance criteria — the type lives in `src/types.ts` as the spec instructs; only the *loading/validation logic* lives in a separate `src/config/loadConfig.ts` module rather than inline in `cli.tsx` as the spec's other clause suggested. This module-location choice is a deliberate, named deviation (kept from iteration 1's reasoning: isolating file I/O and validation from pure argv-syntax parsing is worth the one small deviation), not a silent one.
2. Implement `loadConfig(cwd: string): PlaywrightTuiConfig` per Acceptance Criterion 1: standalone-file-first resolution with the non-object-root guard applied to the standalone file's root and to the `package.json` key's value (**not** to `package.json`'s own root, which falls through silently per Acceptance Criterion 1's scoped fallback), JSON.parse with try/catch producing a path-naming error, per-field type validation, unknown-key rejection. `loadConfig.ts` returns `PlaywrightTuiConfig` values **exactly as read from the file** (an un-normalized `historyFile` string) — it must **not** import `expandHomePath` from `src/cli.tsx` to normalize it internally. `expandHomePath` is a module-local, unexported function in `cli.tsx` (cli.tsx:240-244), and `cli.tsx` runs `main()` at module top level on import (cli.tsx:246) — importing anything from it as a library would execute the CLI. `historyFile` normalization therefore happens exactly once, in the merge step (Implementation Step 4), where `expandHomePath` is already in scope — not as an implementer's choice.
3. Refactor `parseArgs` (cli.tsx:50-170) per Acceptance Criterion 2 — add `explicitKeys` construction alongside the six existing flag-matching branches; `CliOptions`'s shape, the hard defaults at cli.tsx:52-54, and the argv-token-matching loop's control flow are otherwise unchanged.
4. Add the merge step per Acceptance Criterion 3, applied only on the `kind: 'run'` branch (Acceptance Criterion 4) — one visible function, not scattered conditionals, matching Principle 1.
5. Wire `main()` (cli.tsx:23-48) to call `loadConfig(cwd)` and the merge step only for `kind: 'run'`, after `cwd` is known, before constructing `RunController`.
6. Add the `printedCommand` latch to `runHeadless` per Acceptance Criterion 5.
7. Update `buildHelpText()` (cli.tsx:211-238) to mention config file support briefly (one line, pointing at the docs) — not required by the acceptance criteria but keeps `-h`/`--help` output consistent with the new feature; small bonus, not a blocking criterion.
8. Update `docs/docs/usage.md` per Acceptance Criterion 6.
9. Once Epic 1's harness exists: add `src/config/loadConfig.test.ts` per Acceptance Criterion 8.

## Verification Steps

1. `bun run typecheck` — exit code 0.
2. Manual smoke test: run `playwright-tui` with no config file and no relevant flags in a scratch Playwright project with **no `package.json`** in the target directory — confirm behavior is unchanged from before this epic (falls through cleanly to existing hard defaults, no error from the missing `package.json`).
3. Manual smoke test: add a `.playwright-tuirc.json` with `{"runner": "npx"}` in a scratch project, run with no `--runner` flag and `npx` **present** in `PATH` — confirm the headless output's new `Command: npx playwright test ...` line (Acceptance Criterion 5) appears, proving the config value was selected (under the `auto` default the same run would instead print `bunx ...`, per runController.ts:911). Do **not** remove `npx` from `PATH` for this check: `resolveRunner` throws at runController.ts:906, which happens *before* `state.command` is ever assigned (runController.ts:361 vs. the throw at line 351), so the latch would never fire, and the error text lands only in `state.recentOutput`, which `runHeadless` never reads (see Follow-ups) — this positive-selection form is the corrected, actually-observable replacement for iteration 1's broken PATH-exclusion recipe.
4. Manual smoke test: for each of `history`/`historyFile`/`runner`, run once with only a config value set and once with both a config value **and** the opposing CLI flag set — including the `--history` (sets `true`, matches the default) vs. config `{"history": false}` case — confirming the CLI flag always wins. Repeat for both flag spellings of `--history-file`/`--history-file=` and `--runner`/`--runner=`. Observation method differs per field: `runner` is observable via the `Command: ...` line (Acceptance Criterion 5, Step 3 above); `historyFile`/`history` are **not** rendered anywhere in the TUI or headless output (`historyEnabled`/`historyPath` are declared in types.ts:157-158 but never read in `src/tui/` or `runHeadless`) — observe them instead via **file presence**: with `history` enabled, `TimingHistoryStore.save()` writes the resolved `historyFile` path after a run (timingHistoryStore.ts:118-131); with `history: false`, it returns early and writes nothing (timingHistoryStore.ts:119). **Always pass an explicit, scratch `historyFile` for this check** — never run it against the real default path, to avoid clobbering `~/.config/playwright-tui/history.json`.
5. Manual smoke test: add a `.playwright-tuirc.json` with a deliberately wrong-typed value (e.g. `{"runner": 5}`) — confirm a field-naming error is printed via the existing `Error: <message>` path (cli.tsx:248) and the process exits non-zero, and that the message is clearly config-sourced (not, e.g., a coincidental Playwright startup failure in the scratch project). Repeat with malformed JSON (e.g. a trailing comma) — confirm a file-path-naming error. Repeat with a non-object root (e.g. `[1,2,3]` or `null`) — confirm a type-naming error, not a raw `TypeError` stack trace.
6. Manual smoke test: with `.playwright-tuirc.json` present (`{"runner": "npx"}`) *and* a `package.json` `"playwright-tui"` key present with a conflicting value (`{"runner": "bunx"}`) — confirm only the standalone file's value takes effect, observable via the `Command: ...` line.
7. Manual smoke test: `-C` into a scratch project directory with a `.playwright-tuirc.json` (`{"runner": "npx"}`, distinct from the invocation directory's own config, if any) — confirm the config is read from the target (`-C`) directory via the `Command: ...` line, not the invocation directory.
8. Manual smoke test: `--help` and `--version` both still work when the target directory's config file is deliberately invalid (e.g. malformed JSON) — confirm neither is blocked by `loadConfig`.
9. Once Epic 1's harness exists: `bun test` covering Acceptance Criterion 8's scenarios, exit code 0.
10. `bd show playwright-tui-777` acceptance criteria checked off against actual implementation before closing.

Not required for this epic's v1 surface.

## ADR: Config File Support Approach for playwright-tui

**Decision:** Add `.playwright-tuirc.json` / `package.json` `"playwright-tui"`-key config file support via a new `src/config/loadConfig.ts` validation module and a `PlaywrightTuiConfig` type in `src/types.ts` (per the roadmap spec), merged into `parseArgs`'s existing, unchanged `CliOptions` output through one additive `explicitKeys` set and a single visible merge step in `cli.tsx` — Option A-prime, a synthesis found during Architect review that keeps Option A's single-visible-precedence-step win while eliminating its return-type-churn risk.

**Drivers:** (1) `parseArgs` currently has no way to distinguish "explicitly flagged" from "still at default," which any config-precedence design needs. (2) Config lookup must happen after `cwd` is resolved but must never run for `--help`/`--version`. (3) CLI-flag-equivalent config values (`historyFile`) must be normalized identically to their flag counterparts, or they'll silently misbehave. (4) `package.json` is probed as a fallback location, not asserted to be a valid config source, so its own validity can't be conflated with the `"playwright-tui"` key's validity. (5) Unknown-key rejection is a real forward-compatibility tension against the roadmap's own plan to grow the config surface in Epic 3.

**Alternatives considered:**
- *Iteration 1's original Option A (restructure `parseArgs`'s return to a `Partial`)* — rejected in iteration 2 in favor of Option A-prime: the restructure's blast radius (every consumer of `ParseResult` changes) was the plan's own top-ranked risk, and an additive field achieves the same precedence-clarity goal without it.
- *Option B (pre-scan `cwd`, seed `parseArgs`'s locals from config before the flag loop runs)* — a legitimate, closely-argued alternative. Iteration 1 rejected it on a factually incorrect "-C ordering" claim; corrected in iteration 2 to the real reason: a `resolveCwd` pre-scan would duplicate `-C`/`--`/early-return handling in two places that must stay in sync, and loses the "assigning the local is the explicit-override signal" property that Epic 3's fourth config field may need.
- *Option C (always load config from `process.cwd()`, ignoring `-C`)* — rejected outright: breaks the documented `-C`/`--cwd` use case, since a project-local config in the `-C` target would never be found.
- *Normalizing `historyFile` inside `loadConfig.ts` itself* — rejected during iteration-2 review: `expandHomePath` lives in `cli.tsx`, which executes `main()` on import, so importing it into `loadConfig.ts` would be unsafe; normalization is pinned to the merge step in `cli.tsx` instead, where `expandHomePath` is already in scope.
- *Treating any `package.json` read/parse failure as a fail-fast error, matching the standalone file's treatment* — rejected: most target directories have a `package.json` that has nothing to do with playwright-tui, so treating its unrelated validity as a config error would break normal usage; fail-fast is scoped to only apply once a `"playwright-tui"` key is actually found.

**Why chosen:** Every element was independently found and cross-verified by two reviewers across two consensus iterations, working from the real source rather than assumptions — both iteration-2 reviews report zero remaining bad citations, and the architecture itself (Option A-prime, the two-tier `package.json` fail-fast scoping, the merge-step-only normalization) was confirmed correct and stable between iterations, with only verification-layer and validation-edge-case defects remaining by the second pass.

**Consequences:** The three flag-matching branches for `historyEnabled`/`historyFilePath`/`runner` now each carry two obligations (assign the value, register `explicitKeys`) — a missed registration is invisible to `tsc` and only caught by a test/manual check exercising that exact flag spelling, which Acceptance Criterion 8 and Verification Step 4 now both require. Unknown-key rejection is a forward-compatibility ratchet against Epic 3's planned config growth, mitigated by reserving `"$schema"` (done) and version-naming error messages (deferred as a Follow-up). `history`/`historyFile` have no direct TUI/headless observability today — verification relies on file-presence side effects instead, a workaround rather than a fix.

**Follow-ups:** Name the running version in unknown-key error messages. Keep `README.md`'s options table in sync with `docs/docs/usage.md`'s new config-file section (currently in no epic's explicit scope). Consider a general fix for headless-mode error/state visibility (`state.statusText`, `state.recentOutput`, `state.historyEnabled`/`historyPath` are all currently unread by `runHeadless` or the Dashboard) in a later epic.
