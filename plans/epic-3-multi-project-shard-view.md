## RALPLAN-DR Summary

**Principles**
1. Single-project, non-sharded runs are visually and behaviorally unchanged — every project-grouping code path is gated on **the derived tab list having more than one entry** (the union of `state.projectTargets` and observed `projectStats` keys, per Acceptance Criterion 4 — not `state.projectTargets.length > 1` alone, which was found during review to under-gate the header indicator relative to every other gate in an unnamed-project scenario), and shard display is gated on `state.shard !== null`. Never active by default.
2. Screen-space degradation at high project counts must be O(1), but this epic must **honestly acknowledge, not hide, the separate degradation mode in fixed-size event buffers** (`MAX_ACTIVITY_LINES`, `MAX_FAILURES`, `MAX_RECENT_FAILURES`, runController.ts:43-45) that project-filtering does not solve — corrected during review after the original draft conflated "O(1) in screen space" with "no degradation," which is false: those buffers are global and evicted in wall-clock order across all projects, so a low-activity project can silently show near-zero entries while a noisy sibling project has consumed the whole buffer.
3. Both live copies of the Playwright reporter (`reporter/playwrightTuiReporter.cjs` and the embedded `FALLBACK_REPORTER_SOURCE` duplicate in `runController.ts:48-236`) must be updated identically for any reporter-side change — a lesson carried over from Epic 1's review. The project+file key is built via string concatenation (`project + '|' + file`), not a template literal, specifically to avoid the embedded copy's existing escaping fragility (runController.ts:60, :215) — a new escaping trap found during this epic's own review.
4. New per-project state (aggregated stats, shard info) is read defensively — Playwright's reporter API surface (`config.shard`, in particular) isn't a compile-time dependency of this repo, so all new fields are optional and consumed with fallbacks, never assumed present.
5. **The project name a test belongs to must be derived correctly before any of this epic's other work is meaningful** — found during review to be a **pre-existing, high-confidence-but-unverified bug** in `describeTest` (both reporter copies) that this epic's entire design was, in its first draft, built on top of without question. See Decision Driver 5 and Implementation Step 0.
6. Tests for this epic's new logic are added once Epic 1's `bun test` harness exists, mirroring Epic 1/Epic 2's sequencing.

**Decision Drivers**
1. `RunController`'s current file-progress tracking is **not** project-aware: `initializeFileProgress` (runController.ts:635-651) and `adjustFileProgress` (runController.ts:834-851) key `fileProgressMap` by `file` alone, and the reporter's own `onBegin` (`playwrightTuiReporter.cjs:52-96`) aggregates `fileTotals` by file across *all* projects before the event is even emitted. Meaningful per-project grouping requires a project-aware key at both layers.
2. Ink's rendering primitives and the existing row-budget math (`Dashboard.tsx:224-239`) are already a tight, interdependent layout; any mechanism that partitions row budgets proportionally by project count degrades unboundedly as project count grows.
3. `RunState.workers`, `RunState.recentActivity`, and `RunState.failedTests` already carry a `project` field per entry; only `FileProgressViewState` lacks one.
4. Playwright's `FullConfig.shard` must be read defensively (`config?.shard`), since this repo has no compile-time reference to Playwright's types.
5. **`describeTest` (`playwrightTuiReporter.cjs:162-177`, and the identical logic in the embedded copy) derives `project` as `safeTitlePath[0] ?? 'default'`.** Playwright's `TestCase.titlePath()` walks from the **root** suite, whose title is the empty string — the root suite entry *is* included in `titlePath()`'s output (only anonymous `describe` blocks are skipped). Playwright's own base reporter destructures `titlePath()` as `const [, projectName, , ...titles] = test.titlePath()` (comment: `// root, project, file, ...describes, test`), meaning index **1**, not index 0, is the project name. If this repo's `describeTest` has the same off-by-one, every event today carries `project: ''` (the empty root title, not `'default'`, since `''` is not nullish — the `?? 'default'` fallback never fires), and the per-project title displayed to users (`safeTitlePath.slice(1).join(' > ')`) is prefixed with the actual project name instead of starting clean. **This repo has no `@playwright/test` dependency to verify this against at plan-writing time** (no compile-time or runtime access to Playwright's actual `titlePath()` behavior) — this is a high-confidence reading of upstream Playwright source and convention, not a verified observation, and it **must** be confirmed against a real Playwright installation before any of this epic's other implementation steps proceed (Implementation Step 0). If confirmed, fixing it is a **prerequisite bug fix**, tracked and executed before this epic's own new code, not bundled invisibly into it — because it also changes `fingerprint` (`${project}|${file}|${title}`), which invalidates existing entries in users' persisted timing-history files (a compatibility consideration of its own, separate from this epic's feature work).

**Viable Options**

- **Option A — Project-tabs: one active project at a time for spec-files/activity/failures panels, cycled by a new keybind; the worker panel stays unfiltered but labeled (Recommended, revised from iteration 1).** Add `state.shard` and project-aware `FileProgressViewState`/`fileProgressMap` keying (via a `(project, file)` pair passed to `adjustFileProgress`, not a pre-joined string, to guarantee single-project behavior is bit-for-bit unchanged — see Acceptance Criterion 3). Add `activeProjectIndex` cycled by a new `p` keybind, only active when **the derived tab list** (Acceptance Criterion 4) has more than one entry — this single gate is used everywhere (tab cycling, panel filtering, the header indicator, the summary breakdown, the keybind hint), not `projectTargets.length > 1` in some places and the derived list in others, which review found to be an internal inconsistency in an earlier draft. The spec-files, activity, and failures panels are filtered to the active project. **The worker panel is explicitly excluded from this filtering but gains a project label on `WorkerRow`** (see Decision Driver/Risk below — workers are a shared machine-level resource, not a per-project one, and filtering them produces flickering, a badge/content mismatch, and answers the wrong question; labeling satisfies the roadmap spec's "group/label" wording without either problem). The summary panel separately tracks `state.projectStats`, updated in the same call sites as the existing global counters, not derived by re-scanning arrays.
  - Pros: screen space usage for the three project-scoped panels is O(1) in project count — exactly today's single-project layout, just re-scoped. Reuses every existing rendering component with one small, explicit exception (`WorkerRow` gains a project label — a real, if small, change, not the "requires no change at all" claim an earlier draft made). Single-project runs are unaffected.
  - Cons: a user can't see two projects' spec-file progress simultaneously without switching. **Also, contrary to iteration 1's framing, this does not eliminate 1/N degradation — it relocates it from screen space (visible, where the user can tell it's happening) into the global, fixed-size activity/failure ring buffers (invisible, where they can't).** This is now treated as an honestly-documented limitation (Acceptance Criterion 7, Follow-ups), not a solved problem.

- **Option B — Inline grouping with per-project sub-headers, proportional row budgets.** Rejected: partitioning `leftSpecRows`/`rightWorkersRows` proportionally by project count has no graceful floor — at 6+ projects, sub-headers and padding consume most of an already-tight row budget, leaving near-zero visible rows per project. This is a worse, *and visible*, version of the same degradation Option A has invisibly.

- **Option B-prime — Flat, sorted, scrollable list with project group headers, no row-budget partitioning at all.** Considered during review as the strong form of Option B: sort `syncFileProgress`'s output by `(project, file)` instead of `file` alone, render a group-header row when the project changes between adjacent entries, and pass the result through the **existing, unchanged** `windowStart`/slice machinery (Dashboard.tsx:241, :844-849) — the same fixed-size scrolling window this codebase already uses for arbitrarily-long single-project file lists today. This genuinely is O(1) in screen space (the window size doesn't change), and it keeps the 1/N incompleteness *visible* (a 1,000-row list scrolled to 12 visible rows is honestly a long list; a project tab showing near-empty panels looks identical to "nothing happened"). It also preserves cross-project comparison (seeing two projects' progress on adjacent rows) that Option A gives up.
  - **Declined, not unconsidered:** Option A is kept instead because the roadmap spec's "group/label" requirement is satisfied by both approaches (Option A now additionally labels, not just filters, per Acceptance Criterion 4's `WorkerRow` change carried through consistently), and Option A's per-panel scoping composes more predictably with the existing `f` (filter) keybind, which already matches `.project` for activity/failures (Dashboard.tsx:72, :82) — extending it to spec-files (Acceptance Criterion 4) gives a second, text-driven way to reach B-prime's outcome without committing to a full list-layout rewrite across three panels in this epic. B-prime remains a reasonable future direction if usage shows the tab-switch UX doesn't scale past a handful of projects — tracked as a Follow-up, not dismissed.

- **Option C — Separate, dedicated per-project overlay screen.** Rejected: doesn't satisfy "spec-files and worker panels group/label entries by Playwright project" from the roadmap spec — an overlay is a separate view, not the panels themselves being project-aware, and would require a second, parallel rendering path rather than reusing `SpecRow`/`WorkerRow`. (Option A does not have this problem: `WorkerRow` gains a project label per Acceptance Criterion 4, so it satisfies "group/label" without needing to filter — see that criterion for why filtering the worker panel specifically would be wrong, independent of the labeling requirement.)

**Recommendation:** Option A, with the worker-panel labeled-not-filtered treatment and the honest reframing of what "O(1)" does and doesn't solve. Option B-prime was seriously considered and is a legitimate alternative, declined in favor of Option A's scoping model plus the extended `f` filter rather than dissolved by a flaw — tracked as a Follow-up for reconsideration if real usage warrants it.

## Acceptance Criteria

0. **Prerequisite, blocking:** before implementing any other criterion below, verify against a real Playwright installation (a scratch project with `@playwright/test` installed, multiple named projects configured, and a temporary `console.error(JSON.stringify(test.titlePath()))` instrumented into a copy of `describeTest`, or equivalent) whether `titlePath()[0]` or `titlePath()[1]` is the project name. If index 1 is correct (the expected outcome per Decision Driver 5's upstream-convention reading): fix **both** the `project` derivation (`safeTitlePath[1] || 'default'` — `||` not `??`, since an unnamed project's title is also `''`, which is falsy but not nullish) **and** the paired `title` derivation (`safeTitlePath.slice(3).join(' > ')`, not `slice(1)` — the first three entries are root/project/file, none of which belong in a displayed test title) in **both** reporter copies, via a single shared helper (see Acceptance Criterion 2's `projectOf`/title-derivation consolidation) so the two values can't drift independently. Note in the PR that this changes `fingerprint` (`${project}|${file}|${title}`) for all users, invalidating existing entries in `~/.config/playwright-tui/history.json` (they'll simply be treated as new/unknown tests and re-learned — not a crash, but worth flagging). If index 0 turns out to be correct after all (contradicting the upstream-convention reading), document why in the PR and proceed with this epic's other criteria unchanged.
1. `src/types.ts`: `RunBeginEvent` (types.ts:10-19) gains `shard?: { current: number; total: number } | null`. `FileTotalEventEntry` (types.ts:5-8) gains `project: string`. `FileProgressViewState` (types.ts:77-86) gains `project: string`. `RunState` (types.ts:127-160) gains `shard: { current: number; total: number } | null` (non-optional — the `run-begin` handler assigns it as `event.shard ?? null`, per Acceptance Criterion 3, since `RunBeginEvent.shard` is optional but `RunState.shard` is not, and `exactOptionalPropertyTypes: true` in `tsconfig.json` means this coercion must be explicit) and `projectStats: Record<string, ProjectStatsEntry>`, where `ProjectStatsEntry` has the same counter shape as the existing global counters (`total`, `completed`, `passed`, `failed`, `skipped`, `flaky`).
2. **Both** `reporter/playwrightTuiReporter.cjs`'s `onBegin` and the identical logic inside `runController.ts`'s embedded `FALLBACK_REPORTER_SOURCE` are updated identically: a single module-level helper function (e.g. `projectOf(test)`, returning `test.titlePath()[1] || 'default'` once Acceptance Criterion 0 confirms the index) is introduced and used by **both** `onBegin` (which needs `project` per-file while iterating `suite.allTests()` to build `fileTotals`) and `describeTest` (which needs it per-test) — this is deliberate consolidation: without a shared helper, fixing Acceptance Criterion 0 would otherwise require updating the derivation independently at four sites (two functions × two reporter copies), which is exactly the kind of drift Principle 3 exists to prevent. `fileTotals` aggregation groups by a `(project, file)` pair — the key for the intermediate `Map` is built via **string concatenation** (`project + '|' + file`), not a template literal, to avoid the embedded copy's existing escaping fragility around interpolation (runController.ts:215) being extended into new code; each emitted entry includes its `project` as a separate field (not just baked into a composite key) so the controller can reconstruct or re-key as needed. `shard` is read defensively as `config?.shard ?? null`, with the same numeric-shape validation the reporter already applies to `workers` (`playwrightTuiReporter.cjs:99-100`'s `Number.parseInt`/finite-check pattern) applied to `shard.current`/`shard.total`, so a malformed or partially-`undefined` shard object degrades to `null` rather than rendering `shard undefined/undefined`. Both copies (including the new `projectOf` helper within each) must be verified byte-identical (modulo the pre-existing one-comment drift) after the change.
3. `src/controller/runController.ts`: `adjustFileProgress`'s signature changes to accept `project` and `file` as **separate parameters** (`adjustFileProgress(project: string, file: string, updater: ...)`), building its internal map key by concatenation itself — **not** accepting a pre-joined key from call sites. This is required for Acceptance Criterion 9 (single-project byte-identical behavior): a pre-joined-key design risks a lazily-created `FileProgressViewState` entry (runController.ts:836-847's synthesis-on-miss path) ending up with `file: "chromium|tests/login.spec.ts"` instead of the bare filename, which `SpecRow` renders verbatim — a single-project regression on exactly the path that fires whenever a test runs in a file `onBegin` didn't enumerate. `initializeFileProgress` (runController.ts:635-651, one call site at runController.ts:584) and `fileFingerprintSet` (a `Map`, touched at runController.ts:674-676; its `.clear()` calls at runController.ts:435, :637 are unaffected) are updated to the same two-parameter convention. `adjustFileProgress` itself is called at all nine sites enumerated above (runController.ts:597-599, 609-611, 673-679, 700-702, 708-710, 713-715, 721-723, 728-730, 736-738 — verified complete, no others exist) — each is updated to pass `project` and `file` as separate arguments. `syncFileProgress` (runController.ts:853-857)'s sort comparator changes from `left.file.localeCompare(right.file)` to compare `project` first, then `file` (two projects sharing a file name must not compare equal). `snapshot()` (runController.ts:998-1011) gains a **two-level** defensive copy of `projectStats` — `Object.fromEntries(Object.entries(state.projectStats).map(([key, entry]) => [key, { ...entry }]))`, not a shallow `{ ...state.projectStats }` — matching the existing pattern applied to every other mutable collection in `RunState` (e.g. `workers.map(w => ({ ...w }))` at runController.ts:1003): a shallow copy would still alias the per-project entry *objects* that `finalizeTrackedTest` mutates in place (`entry.passed += 1`), silently reintroducing the exact "numbers don't update, then jump" Ink bug this criterion exists to prevent. `createInitialState` (runController.ts:1014-1049) initializes `shard: null` and `projectStats: {}`. `state.shard` is set from `event.shard` on the `run-begin` handler. `state.projectStats` is initialized in the `run-begin` handler with **`total` seeded per-project from the now-project-aware `event.fileTotals`** (summed per project, per Acceptance Criterion 2) — not left at `0` — since `finalizeTrackedTest` (runController.ts:683-746) has no `total` increment of its own (the existing global `state.totalTests` is likewise only ever set once, at run-begin, runController.ts:576); one entry per `event.projectTargets`, plus lazy creation (with `total: 0`, since a project outside `projectTargets` has no corresponding `fileTotals` to seed from) for any project name encountered that isn't in `projectTargets` — see Acceptance Criterion 4's "unreachable project" handling. The remaining counters (`completed`, `passed`, `failed`, `skipped`, `flaky`) are incremented in `finalizeTrackedTest` alongside every existing global-counter increment, keyed by `event.project`. `resetForRun` clears `projectStats` and `shard` alongside other per-run state.
4. `src/tui/Dashboard.tsx`: `HeaderBar`'s prop signature changes to accept the new shard/project-indicator data as explicit props (it currently takes scalar props — `width`, `version`, `browserTargets`, `workers`, `statusRunning` — not `state` — this is a real signature change, not a drop-in `state` reference) and renders a shard segment (e.g. `shard 2/4`) when shard data is non-null, and an active-project indicator (e.g. `chromium (2/3)`) when **the derived tab list (defined below) has more than one entry** — both appended to the existing right-side text, with `leftWidth`'s truncation budget (`Math.max(8, width - right.length - 1)`) re-verified not to over-truncate the left segment on narrow (80-column) terminals now that `right` can carry more content. **The tab list is derived as the union of `state.projectTargets` and `Object.keys(state.projectStats)`, in a defined order: `projectTargets`' own order first, then any names present only in `projectStats` appended afterward, deduplicated** — not `projectTargets` alone, and not left to `Object.keys`' incidental insertion order, since that order also determines the header's `(2/3)` index and (per Acceptance Criterion 5) which projects survive the summary breakdown's row-budget truncation. This derived tab list — not `state.projectTargets.length > 1` — is **the single gate used everywhere** in this epic: the header indicator above, the `p` key handler below, the panel filtering below, Acceptance Criterion 5's summary breakdown, and Acceptance Criterion 6's keybind hint. Using `projectTargets.length > 1` in some of these places and the derived list in others (as an earlier draft did) would let a one-named-plus-one-unnamed-project scenario filter panels and enable `p` while the header shows no indicator of an active project — an internally inconsistent user experience found during review. A project whose name isn't in Playwright's own `config.projects[].name` list (e.g. an unnamed project among named ones) would otherwise be unreachable in the UI despite emitting real events, which is why the union (not `projectTargets` alone) is required.

   A new `activeProjectIndex` state, defaulting to `0`, is added; a `p` key handler cycles it through the tab list **and resets `selectedFileIndex`/`selectedFailureIndex` to `0`** (the existing clamp effects at Dashboard.tsx:87-93 only fire when a filtered list's *length* changes — switching tabs can produce a same-length but entirely different list, leaving the selection highlight on an unrelated, coincidentally-same-index row otherwise); only effective when the tab list has more than one entry (no-op otherwise, matching existing patterns like `r` being a no-op when `state.failed === 0`). When the tab list has more than one entry: the spec-files panel's `filteredFiles` and the failures panel's `filteredFailures`/activity panel's `filteredActivity` are each additionally filtered to entries matching the active tab's project name, before the existing slicing/windowing logic runs unchanged.

   **The worker panel is NOT filtered by project, but `WorkerRow` gains a project label** (it already receives `worker.project`, currently rendered nowhere — Dashboard.tsx:541-563) so the panel satisfies the roadmap spec's "group/label entries by Playwright project" requirement without filtering: workers are a shared machine-level resource (Playwright's worker pool spans all projects in a run), and per-project *filtering* would (a) make idle worker slots (`project: null`) vanish from the panel entirely since `null` matches no project name, causing visible flicker between 0 and the true worker count, and (b) desync the `WORKERS` badge count (Dashboard.tsx:351, which must stay unfiltered for a meaningful "how busy is my machine" reading) from a filtered row list beneath it — labeling avoids both problems while still satisfying the spec's wording. **Adding the label requires re-budgeting the row, not just adding text**: the hardcoded column-header string (Dashboard.tsx:354-356, currently `'  #  TEST                                              FILE                  TIME'`) needs a `PROJECT` column inserted, and the title-truncation width (Dashboard.tsx:552, `truncate(worker.title, Math.max(8, width - 44))`, alongside the `file` field's 18-column pad and the duration's 7-column pad) needs its budget re-derived to make room — found during review to be missing from the original label-not-filter fix, which specified the label but not its column-width consequence, and the row is already width-tight enough that an unbudgeted addition would either silently squeeze the test title or overflow on 80-column terminals.

   Two explicit empty/edge states are handled: (a) when the active tab's project has received a `run-begin`'s file-progress seeding but zero test events yet — defined precisely as: the project's `projectStats` entry has `completed === 0` **and** no `state.workers` entry currently has that `project` (the `completed === 0` check alone would misfire for an in-flight project with running-but-not-yet-completed tests) — the spec-files panel shows its normal 0/N rows (already true today) but the activity/failures panels show an explicit `"<project> — not started yet"` message instead of the generic `"no completed tests yet"`/`"no failures"` text (`FailureList`'s existing early return, Dashboard.tsx:607-614, gains a prop for this alternate message), so a user tabbed to a not-yet-started project can distinguish "nothing happened here yet" from "the TUI is broken"; (b) `activeProjectIndex` is clamped via a `useEffect` mirroring the existing pattern (Dashboard.tsx:87-93 for `selectedFileIndex`/`selectedFailureIndex`) whenever the tab list's length changes across a rerun, so a stale index from a run with more projects than the current one doesn't point past the end of a shorter list. As a minor consistency improvement now that `FileProgressViewState` carries `project`, the existing `f` filter (which already matches `.project` for activity and failures, Dashboard.tsx:72, :82) is extended to match spec-files entries too (Dashboard.tsx:61-64 currently matches `file` only).
5. `SummaryPanel` gains a per-project breakdown section (only rendered when **the derived tab list** has more than one entry — the same gate as Acceptance Criterion 4), listing each project's `total`/`passed`/`failed`/`skipped` from `state.projectStats`, **ordered by `failed` count descending** (not tab-list order) so that if the section is truncated by the panel's existing `maxRows` slicing, the projects with the most failures — the ones a user most needs to see — are the ones that survive, not an arbitrary prefix of the tab-list order. **No change to `summaryRows`'s row-budget calculation** — this section competes for the same fixed space as the existing sections and is explicitly acknowledged (Acceptance Criterion 7) as itself subject to truncation at high project counts, consistent with this epic's honest framing rather than claiming unbounded coverage.
6. `KeybindBar` shows the `p` keybind hint only when **the derived tab list** has more than one entry (same gate as Acceptance Criterion 4).
7. **Rewritten as a falsifiable, observable requirement** (iteration 1's version — "has no proportional-shrink failure mode to test at a specific threshold" — was a structural claim, not something that could be run and checked, and was also not fully true): a fixture `RunState` with 2 projects and a fixture `RunState` with 20 projects, both otherwise equivalent, produce **identical row counts and panel dimensions** for the spec-files/activity/failures panels (verifying the O(1)-in-screen-space property, once Epic 1's harness exists). **Separately and explicitly documented as a known, accepted limitation** (not silently glossed over): the global activity/failure ring buffers (`MAX_ACTIVITY_LINES` and `MAX_FAILURES` — **not** `MAX_RECENT_FAILURES`, which is written at runController.ts:785 but read by nothing in the current codebase and is therefore not a user-visible limitation worth documenting) are shared across all projects and evicted in wall-clock order, so a low-activity project viewed via its tab can show near-empty panels purely because a noisy sibling project has consumed the shared buffer — this is a real form of degradation at high project counts that project-tabs does not solve, tracked as a Follow-up rather than claimed as fixed.
8. `docs/docs/features.md` documents: the shard index/total header display; the `p` keybind and project-tabs behavior (only active with 2+ observed projects, per the derived tab list); the summary panel's per-project breakdown and its own row-budget bound; that the worker panel is intentionally never project-filtered (only labeled); that single-project runs are unaffected; and the `MAX_ACTIVITY_LINES`/`MAX_FAILURES` ring-buffer cross-project-truncation limitation from Acceptance Criterion 7.
9. No change to single-project, non-sharded run behavior: with a one-entry tab list and `shard === null`, every new code path in Acceptance Criteria 2-6 is inert, and — critically, per Acceptance Criterion 3's separated-parameter design — `fileProgressMap`'s re-keying resolves identically to the prior `file`-only keying for a single project, with no risk of a `project|file`-mangled filename appearing anywhere in the UI.
10. Tests for the controller-side project/shard tracking and the Dashboard-side filtering/cycling logic are added once Epic 1's `bun test` harness exists, covering at minimum: `fileProgressMap` correctly keeps two projects' same-named file as separate entries, each retaining its own bare `file` value (not a mangled composite) — asserted both in the controller's state directly **and** by rendering `SpecRow` and asserting the displayed label is the bare filename (e.g. `tests/login.spec.ts`), not `chromium|tests/login.spec.ts`, since Acceptance Criterion 3's separated-parameter design is this epic's top-rated regression risk and deserves an assertion that doesn't depend on inferring correctness from a count alone; `projectStats.total` is correctly seeded per-project from `fileTotals` (not left at `0`) and its sum across all projects equals `state.totalTests`; `projectStats`'s other counters increment correctly per project and its snapshot is independent of the live mutable object; `p` cycles `activeProjectIndex` through the derived tab list and wraps around; the worker panel's row count and `WORKERS` badge render identically regardless of `activeProjectIndex`, and `WorkerRow`'s project label doesn't truncate the test title below a reasonable minimum width; the not-yet-started-project empty state renders correctly (including the `completed === 0 && no active worker` predicate, not `completed === 0` alone); a stale `activeProjectIndex` from a prior, larger-project-count run is clamped correctly after a rerun; the Acceptance Criterion 7 screen-space-invariance fixture comparison; single-project `RunState` fixtures produce identical output to Epic 1's existing Dashboard tests.

## ADR: Multi-Project/Shard View Approach for playwright-tui

**Decision:** Gate all feature work on an empirical verification of `describeTest`'s Playwright project-name derivation (Acceptance Criterion 0) before any other implementation proceeds. Add project-aware tracking to the controller via a separated-parameter `adjustFileProgress(project, file, updater)` signature and a two-level-copied `projectStats` aggregate. Implement multi-project visibility as project-tabs (one active project at a time for spec-files/activity/failures panels, cycled by a new `p` keybind) with the worker panel labeled but never filtered, plus an honest, explicit acknowledgment that this does not solve — only relocates — degradation in the global activity/failure ring buffers at high project counts.

**Drivers:** (1) The project name a test belongs to is derived via `titlePath()[0]` today, which is very likely off-by-one against Playwright's own convention (`titlePath()[1]`) — everything else in this epic is moot if that's wrong. (2) `fileProgressMap` keying must not risk a mangled composite filename leaking into a single-project run. (3) Workers are a shared machine-level resource; filtering them by project is the wrong operation on that data, even though labeling them satisfies the roadmap spec's "group/label" wording. (4) The roadmap spec's "graceful degradation" requirement is real, but a naive reading conflates "constant screen space" with "no data loss" — the global ring buffers still degrade invisibly under a project-scoped view, and that must be documented, not hidden.

**Alternatives considered:**
- *Option B (inline grouping with proportional row-budget partitioning)* — rejected: no graceful floor at 6+ projects, worse than Option A on both axes (visible AND severe degradation).
- *Option B-prime (flat, `(project, file)`-sorted, scrollable list with group headers, reusing the existing fixed-size scroll window)* — a genuinely strong alternative, found during review to also be O(1) in screen space while keeping incompleteness visible rather than hidden, and preserving cross-project comparison that Option A gives up. Declined in favor of Option A plus an extended `f` filter, on the grounds that Option A's per-panel scoping composes more predictably with existing UI, not because B-prime has a structural flaw — recorded as a Follow-up for reconsideration if tab-based UX doesn't scale in practice.
- *Option C (separate overlay screen)* — rejected: doesn't satisfy the roadmap spec's "group/label" wording for the actual panels, would require a parallel rendering path.
- *Filtering the worker panel by project* — rejected in favor of labeling it: filtering causes visible flicker on idle slots (`project: null`) and desyncs the `WORKERS` badge from the panel's row count; labeling satisfies the spec's wording without either problem.

**Why chosen:** The Architect's two-iteration review found and the Planner resolved: a plan-breaking unverified assumption (converted into a gated, falsifiable prerequisite rather than either ignored or silently assumed), an internal contradiction between the degradation claim and its own risk table (resolved by honest reframing rather than a false claim), and several controller-layer correctness gaps (aliasing, comparator, signature) that would have caused silent data corruption or single-project regressions. This is the most heavily-scrutinized of the three epics planned so far specifically because it touches the most interconnected, stateful part of the codebase (the reporter/controller/Dashboard pipeline) and rests on an assumption about a third-party library's undocumented-in-this-repo behavior.

**Consequences:** Implementation cannot begin until Acceptance Criterion 0's Playwright-installation probe is complete — this is a real, if small, sequencing cost. If the probe confirms the bug, existing users' timing-history files are silently invalidated (re-learned, not lost or crashed). The global ring-buffer degradation limitation is accepted as a known gap, not fixed in this epic — tracked as a Follow-up. This plan's consensus basis is asymmetric: an unusually thorough Architect review (two full iterations, explicit source verification throughout) without a completed independent Critic pass, noted transparently in this document's Status line rather than concealed.

**Follow-ups:** Complete Acceptance Criterion 0's probe as the first implementation action. Consider Option B-prime (grouped/scrolled list) if project-tab cycling proves unwieldy in practice. Address the global ring-buffer cross-project truncation in a future epic (per-project buffers or an eviction indicator). Reserve the same forward-compatibility care (`$schema`-style allowances) that Epic 2 applied, if this epic's config-reading soft-dependency on Epic 2 (Implementation Step 10) is exercised.
